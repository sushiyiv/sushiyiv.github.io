    概述#

    将 VMware 虚拟机文件夹移动到新的位置后，虚拟机网络异常。可能是选择了 “I moved it”，VMware 保留了原来的 UUID 和 MAC 地址，虽然网卡配置仍然存在，但仅重新添加 Network Adapter 并不能恢复网络。必须为虚拟网卡重新生成一个新的 MAC 地址后，Linux 才能够正确识别并建立网络链路。

    在重新生成 MAC 地址后，手动执行：

    sudo ip link set ens33 up sudo dhclient ens33

    即可正常获取 DHCP 地址并联网。

    但重启系统后，网络再次失效。进一步排查发现，问题已经从网卡识别转变为 NetworkManager 未管理 ens33（unmanaged），导致系统开机不会自动启用网卡和自动获取 DHCP 地址。通过修改 NetworkManager 配置，使 ens33 恢复为 managed 状态后，最终实现了开机自动联网。

    正文#

    这次问题其实是一个比较完整的 VMware + Ubuntu + NetworkManager 故障排查案例。我按照实际排查过程整理了一份完整流程，以后遇到类似问题可以直接按这个思路排查。

    VMware Ubuntu 网卡无法联网故障排查记录#

    一、故障现象#

    虚拟机正常启动，但无法联网。

    VMware#

    • 网络模式：NAT
    • Connected 为灰色无法勾选
    • Connected at power on 已勾选

    Ubuntu#

    ip addr

    结果：

    ens33: state DOWN

    没有 IPv4 地址。

    二、首先确认 VMware 是否正常#

    查看虚拟机配置(.vmx)

    确认存在：

    ethernet0.present = "TRUE"
ethernet0.connectionType = "nat"
ethernet0.virtualDev = "e1000"
ethernet0.generatedAddress = "00:0c:29:..."

    说明：

    • VMware 网卡存在
    • NAT 正常
    • MAC 已生成

    三、检查宿主机 VMware 虚拟网卡#

    Windows：

    ipconfig

    查看：

    VMware Network Adapter VMnet8

    应该类似：

    IPv4 192.168.xx.1

    说明 NAT 网络存在。

    四、检查 Ubuntu 网卡#

    查看：

    ip addr

    发现：

    ens33 DOWN

    先启动网卡：

    sudo ip link set ens33 up

    再次查看：

    ip addr

    结果：

    ens33 UP

    说明：

    • 网卡驱动正常
    • 内核识别正常

    五、检查物理链路#

    执行：

    sudo ethtool ens33

    结果：

    Link detected: yes

    说明：

    • VMware 已连接
    • 驱动正常
    • 不是硬件问题

    六、手动获取 DHCP#

    执行：

    sudo dhclient -v ens33

    结果：

    DHCPOFFER
DHCPACK
bound to 192.168.16.128

    再次：

    ip addr

    得到：

    192.168.16.xxx

    说明：

    • VMware NAT 正常
    • DHCP 正常
    • 网络实际上没有问题

    问题变成：

    为什么开机不会自动获取 IP？

    七、发现 NetworkManager 不管理网卡#

    查看：

    nmcli device

    结果：

    ens33 unmanaged

    继续查看：

    nmcli -f GENERAL.NM-MANAGED device show ens33

    结果：

    GENERAL.NM-MANAGED: no

    说明：

    NetworkManager 完全没有接管 ens33。

    八、检查 NetworkManager 配置#

    查看：

    NetworkManager --print-config

    发现：

    [keyfile]
unmanaged-devices=...

    于是创建覆盖配置：

    sudo nano /etc/NetworkManager/conf.d/10-managed.conf

    内容：

    [keyfile]
unmanaged-devices=none

    九、修正 NetworkManager 配置错误#

    之前由于配置写错：

    NetworkManager is not running

    修正配置：

    sudo systemctl restart NetworkManager

    恢复正常。

    十、检查 Netplan#

    查看：

    cat /etc/netplan/*.yaml

    内容：

    network:
  version: 2
  renderer: NetworkManager

    说明 renderer 正确。

    但是：

    Permissions too open

    修复权限：

    sudo chmod 600 /etc/netplan/*.yaml

    重新生成：

    sudo netplan generate
sudo netplan apply

    十一、创建 NetworkManager 连接#

    查看：

    nmcli connection show

    没有连接时：

    sudo nmcli connection add \
type ethernet \
ifname ens33 \
con-name ens33 \
ipv4.method auto \
ipv6.method auto

    十二、最终验证#

    查看：

    nmcli device

    结果：

    ens33 ethernet connected ens33
lo loopback unmanaged --

    这是正常状态。

    查看：

    ip addr

    得到：

    192.168.xx.xx

    说明 DHCP 自动获取成功。

    十三、最终保留配置#

    /etc/netplan/01-network-manager-all.yaml#

    network:
  version: 2
  renderer: NetworkManager

    /etc/NetworkManager/conf.d/10-managed.conf#

    [keyfile]
unmanaged-devices=none

    十四、故障根因分析#

    整个故障实际上分为两个阶段：

    第一阶段：网卡未自动启动#

    表现：

    ens33 DOWN

    可以手动：

    ip link set ens33 up
dhclient ens33

    恢复网络。

    说明：

    • VMware 正常
    • 驱动正常
    • DHCP 正常

    第二阶段：NetworkManager 不管理网卡#

    表现：

    ens33 unmanaged
GENERAL.NM-MANAGED=no

    导致：

    • 开机不会启动网卡
    • 不会自动获取 DHCP
    • 每次都要手动执行 ip link 和 dhclient

    通过修正 NetworkManager 配置并重新加载后，ens33 恢复为 connected。

    这次涉及到的知识点#

    这次故障几乎覆盖了 Linux 网络管理的完整链路：

    VMware 虚拟硬件
        │
        ▼
Linux 内核驱动（e1000）
        │
        ▼
网卡状态（ip link）
        │
        ▼
DHCP（dhclient）
        │
        ▼
Netplan（renderer）
        │
        ▼
NetworkManager（nmcli）
        │
        ▼
网络连接（connection）

    对于学习 Linux 运维和网络工程来说，这是一个非常典型的综合排障案例。不仅验证了硬件、驱动、DHCP 是否正常，还逐层排查了 NetworkManager 和 Netplan 的配置，基本涵盖了 Ubuntu 桌面版网络故障定位的核心思路。
